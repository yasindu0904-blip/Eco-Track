1. Mission and success definition

Member 1 owns the authorization foundation and the final integration of the team’s isolated feature modules. Authentication is already complete: Supabase verifies identity, the backend synchronizes the EcoTrack profile through Prisma, the web sends bearer tokens, role-aware login works, and the existing Super Admin check is proven. This work must extend that foundation without replacing it.

Core outcome: every organization application, Super Admin review, notification, and future organization-scoped request is allowed or denied by backend authorization built from trusted profile and membership data. Frontend visibility is never treated as security.

Deliverables

  • Install and configure @casl/ability and @casl/prisma.
  • Define stable application actions and subjects.
  • Create typed ability rules from platform role and organization membership.
  • Create ability-building and authorization middleware.
  • Create tenant/membership middleware for organization-scoped operations.
  • Extend Express request typing without weakening existing authentication types.
  • Write negative and cross-organization tests.
  • Integrate Member 2 and Member 3 routers into backend/src/app.ts.
  • Integrate Member 2 and Member 3 pages into the real authenticated web flow.
  • Run complete integration checks and protect shared files during merge.

5. Authorization architecture

Supabase Auth -> proves identity and returns a verified user Prisma repositories -> load profile, platform role, organization membership and status CASL ability factory -> converts trusted context into permitted actions and subjects Express middleware -> enforces the ability before controllers Service and repository -> revalidate business invariants and scope database writes

Required request order

Route typeRequired middleware orderReason
Citizen creates organization applicationauthenticate -> ability -> authorize Create -> controllerNo organization tenant exists yet; identity/profile is enough.
Citizen reads own applicationauthenticate -> ability -> authorize ReadOwn -> controllerRepository must also filter by authenticated profile ID.
Super Admin pending/review routeauthenticate -> ability -> authorize Review/Approve/Decline -> controllerPlatform-scoped authorization; no organization membership is required.
Future organization-owned routeauthenticate -> tenant -> ability -> authorize -> controllerMembership and organization equality must be verified before access.
User notificationsauthenticate -> ability -> authorize ReadOwn -> controllerRepository filters by authenticated recipient ID.

7. Ability factory rules

Trusted inputs

The ability factory may use only data loaded by backend authentication/repositories:

  • Authenticated EcoTrack profile ID
  • Platform role and account status
  • Active organization memberships
  • Membership role and membership status
  • Verified active organization/tenant context when present

Initial policy matrix

PrincipalAllowedExplicitly not allowed
Active USERCreate an application; read own application; read own notificationsReview other applications; approve/decline; create own ORG_ADMIN role
Active SUPER_ADMINList/review pending applications; approve/decline; view verification/service-area details; platform governanceAct as an organization admin without a real membership; ordinary tenant cleanup work
Active ORG_ADMIN membershipFuture organization-scoped administration for that organization onlyAccess another organization by changing an ID; platform Super Admin review
Suspended/archived profileNothing protectedAll protected operations
Suspended/left/removed membershipNo organization-scoped operationsAll tenant actions using that membership

Defense in depth

CASL answers whether an action is generally allowed. Repositories/services still scope queries using trusted IDs. For example, “read own application” must query using both application ID and requestedByUserId = request.authentication.profile.id. Never load by application ID and rely only on a frontend comparison.

8. Middleware and request context

Ability middleware

  • Requires request.authentication.
  • Loads any additional memberships needed for the request.
  • Builds the ability through the factory.
  • Attaches the typed ability to the request.
  • Forwards unexpected errors to central error middleware.

Authorize middleware

  • Accepts a required action and subject.
  • Calls the request ability.
  • Returns a consistent 403 FORBIDDEN ApplicationError when denied.
  • Contains no Prisma queries and no response-shaping controller logic.

Tenant middleware

Tenant middleware is required only when a route is truly organization-scoped. It must:

  1. Read the organization ID from the route or another trusted route context.
  2. Validate ID format.
  3. Query a membership using authenticated profile ID plus organization ID.
  4. Require active membership and a usable organization status.
  5. Attach organization and membership context to the request.
  6. Reject direct-ID attacks with 403 without revealing private tenant data.

Express type augmentation

Extend the existing declaration rather than replace it:

declare global {
  namespace Express {
    interface Request {
      authentication: AuthenticationContext;
      ability?: AppAbility;
      tenant?: OrganizationTenantContext;
    }
  }
}

Type declarations describe properties; middleware creates the actual runtime values.

Member 2 and Member 3 export router factories and dependency objects. Member 1 mounts them. Do not import repositories directly into app.ts; routers receive dependencies or import their module dependency object.

Integration review checklist

  • No duplicate /api/v1 prefix.
  • Authentication runs before ability/tenant middleware.
  • Authorization runs before the controller.
  • Controller delegates business rules to the service.
  • Service delegates database operations to repository/transaction helpers.
  • notFound and error middleware remain last.
  • No route trusts body-supplied actor IDs or roles.

11. Shared frontend integration

The current web authentication state must remain intact. Member 1 integrates exported pages into the signed-in experience and routes users by capability:

Authenticated USER -> organization application/status UI Authenticated SUPER_ADMIN -> pending organization review UI Unauthorized frontend state -> hide action for UX -> backend still rejects direct calls

Use the existing apiClient.ts so bearer tokens and backend errors remain consistent. Do not put CASL alone in the browser and treat it as enforcement. Browser authorization is presentation only.

12. Testing strategy

Authorization unit tests

  • Active USER can create application.
  • USER cannot review/approve/decline.
  • Active SUPER_ADMIN can review/approve/decline.
  • Suspended SUPER_ADMIN cannot perform review.
  • ORG_ADMIN rules contain organization conditions.
  • Suspended/left membership produces no tenant capability.

Middleware tests

  • Missing authentication produces 401.
  • Missing ability context fails safely.
  • Denied action produces stable 403 JSON.
  • Tenant middleware rejects membership from another organization.
  • Tenant middleware rejects suspended organization/membership.

Cross-organization tests

Cross-organization tests are mandatory. A successful same-organization test does not prove tenant security.
  • Organization A admin cannot read or update Organization B private records by changing an ID.
  • A membership for A cannot authorize a route for B.
  • Frontend-supplied role and actor IDs are ignored.
  • A normal user cannot call Super Admin endpoints directly even if the button is hidden.
  • Review queries never leak documents/notes to unauthorized accounts.
