1. Mission and scope

Member 3 owns two separate concerns and therefore uses two separate branches:

  1. Super Admin organization review on the backend and web.
  2. Supabase authentication in the empty mobile Android Studio project.
Core review outcome: an active SUPER_ADMIN can list and inspect pending organization applications, approve or decline exactly once, record reviewer/audit information, notify the requester, and create the requester’s first active ORG_ADMIN membership only on approval.
Core mobile outcome: Android uses the same Supabase project and passwordless identity model, securely handles deep-link/PKCE sessions, sends the Supabase access token as a bearer token to the existing Express backend, loads /auth/me, persists session state, and signs out correctly.

Excluded

  • Database schema and migration ownership.
  • Citizen organization application submission.
  • GN boundary import.
  • Incidents, coordinates, point-to-GN lookup, dashboards and maps.

8. Approval transaction

Approval must be atomic and conditional. The application must still be PENDING_REVIEW when the transaction writes. This prevents two Super Admin sessions from approving/declining the same application concurrently.

authenticate active user -> CASL authorizes Approve -> validate organization ID and optional notes -> Prisma transaction: conditionally transition Organization PENDING_REVIEW -> ACTIVE set reviewedByUserId from authenticated Super Admin profile set reviewedAt and activatedAt update pending selected service areas -> ACTIVE/approved create requester OrganizationMembership: role = ORG_ADMIN status = ACTIVE source = FIRST_ADMIN create approval AuditLog create ORGANIZATION_APPROVED Notification for requester -> commit -> return safe approved result

Critical checks

  • Reviewer ID comes from request.authentication.profile.id, never request body.
  • Organization must exist and still be pending.
  • Requester profile must still exist and be eligible for membership.
  • Selected service areas must be in an approvable state.
  • Unique organization/user membership constraint must be respected.
  • If the requester is already a member because of data inconsistency, fail safely and investigate; do not create duplicate membership.
  • Transaction rollback must leave no partially active organization, missing admin, audit or notification.

Concurrency strategy

Use a conditional update/updateMany or another reviewed transaction pattern that proves the current state is pending. If zero rows transition, return a conflict:

409 ORGANIZATION_REVIEW_CONFLICT
"This organization application has already been reviewed or changed."

9. Decline transaction

authenticate active user -> CASL authorizes Decline -> validate organization ID and review notes -> Prisma transaction: conditionally transition Organization PENDING_REVIEW -> DECLINED set reviewer, reviewedAt and reviewNotes transition pending service areas -> DECLINED create decline AuditLog create ORGANIZATION_DECLINED Notification DO NOT create membership DO NOT set activatedAt -> commit -> return safe declined result

Decide with the team whether review notes are mandatory for decline; recommended: require a useful bounded note. Do not include sensitive internal-only comments in the user-visible notification unless explicitly separated.

entityTypeOrganization

metadataSafe old/new status, selected-area count, reason code; no secrets

Notification

  • Recipient is organization.requestedByUserId, not body data.
  • Approval message states organization became active and requester is now ORG_ADMIN.
  • Decline message states declined status and safe review notes/reason.
  • Notification is created inside the same transaction as review state.
  • Notification listing filters by authenticated recipient ID.
  • WebSockets are not required; load/poll notifications through REST for this milestone.

11. Authorization and security

Member 1 defines action and subject constants. Member 3 consumes them; do not create a second local permission vocabulary.

Review route order

router.post(
  "/super-admin/organization-applications/:organizationId/approve",
  authenticate,
  buildAbility,
  authorize(Actions.Approve, Subjects.OrganizationApplication),
  approveOrganizationApplicationController,
);

Security requirements

  • Active SUPER_ADMIN platform role is required for all review routes.
  • Normal USER and ORG_ADMIN membership alone are insufficient.
  • Frontend button visibility is not authorization.
  • Review list/detail must not leak to unauthorized direct requests.
  • Reviewer and actor IDs always come from authentication context.
  • All errors use ApplicationError and central error middleware.
  • Unexpected Prisma errors do not expose database details.
  • Use pagination and bounded filters for lists.

13. Android project and Supabase client

The repository’s mobile directory is currently empty. Create the Android Studio project there on the separate mobile branch. Use Kotlin and the agreed UI approach (Jetpack Compose if selected by the team).

Initial requirements

  • Internet permission in AndroidManifest.xml.
  • Supabase Kotlin client and Auth module.
  • Compatible Ktor client engine and Kotlin serialization as required by the chosen library version.
  • Supabase project URL and publishable key supplied through a non-secret build configuration.
  • No Supabase secret/service-role key in mobile source, resources or build output.
  • Backend API base URL configurable for emulator/device development.
Networking note: Android emulator cannot use localhost to reach the developer computer. Use the emulator host address (commonly 10.0.2.2) or an agreed LAN/development URL, and expose the backend carefully only as required.

Supabase client responsibilities

  • Install Auth.
  • Use PKCE flow.
  • Configure deep-link scheme and host.
  • Persist/restore session through the library.
  • Observe authenticated, initializing, refresh failure and signed-out states.

14. Android magic-link and PKCE flow

Supabase dashboard

Add the agreed Android deep-link URL to Supabase Authentication redirect URLs. Use an app-specific scheme/host, for example:

ecotrack://auth-callback

The exact scheme and host must match Android manifest intent filters and the Supabase Auth client configuration.

Android flow

User enters email -> Android calls Supabase signInWith(OTP) for email -> Custom SMTP sends magic link -> user opens link on Android -> Android deep link opens EcoTrack -> MainActivity passes intent to Supabase handleDeeplinks(intent) -> PKCE code/session is handled by the Auth plugin -> sessionStatus becomes Authenticated -> Android sends access token to Express /api/v1/auth/me -> backend verifies token and returns EcoTrack profile -> authenticated mobile UI appears

Conceptual Kotlin configuration

val supabase = createSupabaseClient(
    supabaseUrl = BuildConfig.SUPABASE_URL,
    supabaseKey = BuildConfig.SUPABASE_PUBLISHABLE_KEY,
) {
    install(Auth) {
        flowType = FlowType.PKCE
        scheme = "ecotrack"
        host = "auth-callback"
    }
}

Use the current Supabase Kotlin documentation while implementing because Gradle coordinates and APIs must match the selected library version.

Deep-link handling

  • Add the manifest intent filter for the exact scheme/host.
  • Call supabase.handleDeeplinks(intent) early in activity startup as required by the library.
  • Handle a new intent if the activity is reused.
  • Display expired/invalid link errors safely.
  • PKCE requires the code verifier from the initiating client; test the complete same-device flow.
  • Do not log magic-link parameters, access tokens or refresh tokens.

15. Android backend API integration

Request

GET /api/v1/auth/me
Authorization: Bearer <Supabase access token>
Accept: application/json

The mobile application must use the same backend contract as web. It does not query private EcoTrack application tables directly through Supabase. The backend owns profile provisioning, account-status checks and authorization.

Mobile auth state

StateUI/behavior
InitializingLoading state; do not briefly show protected UI.
Not authenticatedEmail magic-link form.
Email sentClear same-device link instructions and resend cooldown.
Authenticated, profile loadingSend bearer request to /auth/me.
Authenticated and activeShow authenticated profile/home appropriate to milestone.
Account inactiveShow backend message; do not show protected app.
Refresh failureClear/repair session and return to sign-in safely.
Signed outRemove session state and show login.

Sign-out

Call Supabase sign-out, observe the session state, clear in-memory EcoTrack profile data, and navigate to login. Test for stale-request races similar to the web fix: an older profile request must not overwrite the newer signed-out state.

16. Testing strategy

Review service/repository tests

  • Normal USER receives 403 for every review endpoint.
  • Active SUPER_ADMIN can list pending and read review details.
  • Suspended Super Admin is rejected.
  • Approval transitions exactly one pending organization.
  • Approval activates selected service areas.
  • Approval creates exactly one FIRST_ADMIN membership.
  • Approval creates audit and requester notification.
  • Decline creates no membership and no activatedAt.
  • Decline creates audit and requester notification.
  • Second/concurrent review returns 409 and creates no duplicates.
  • Any transaction failure rolls back every write.
  • Reviewer ID/body spoofing is impossible.
  • Notification list returns only authenticated recipient records.

Web tests/manual checks

  • Pending list loading/empty/error/success states.
  • Detail displays selected GN names/codes and review metadata.
  • Approve/decline buttons disabled while pending.
  • 409 conflict is explained and list refreshes.
  • Normal user cannot see review navigation and direct API still returns 403.
  • Build and lint pass.

Android tests/manual checks

  • App contains only publishable key, never service key.
  • Email sends through configured SMTP.
  • Magic link opens the app through exact deep-link scheme/host.
  • PKCE session completes on same device.
  • Session survives activity/app restart as intended.
  • Bearer token reaches backend and /auth/me returns profile.
  • Invalid/expired token produces safe login/error state.
  • Sign-out remains signed out after restart.
  • Access/refresh tokens never appear in logs.
