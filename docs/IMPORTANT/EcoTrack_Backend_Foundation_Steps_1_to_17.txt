EcoTrack Backend Foundation — Canonical Record of Steps 1–17
================================================================

Purpose
-------
This document records the backend foundation work completed so far for EcoTrack.
It is intended to be given to Codex so implementation can continue without losing
the architectural and technical decisions already made.

Important workflow change
-------------------------
- ChatGPT is used for research, architecture discussion, explanations, and decision-making.
- Codex is used for repository inspection, coding, editing, running commands, and tests.
- Codex must inspect the current repository before changing files.
- Existing package versions created by npm must be preserved unless an upgrade is explicitly requested.
- Never place real passwords, API keys, database URLs, JWTs, access tokens, or service-role keys in source files or documentation.

Current project architecture
----------------------------
Repository:

Eco-Track/
├── backend/   # Node.js + Express + TypeScript REST API
├── web/       # React + TypeScript + Vite admin dashboard
├── mobile/    # React Native + Expo + TypeScript
├── docs/
├── .editorconfig
├── .gitignore
└── README.md

Main backend architecture:
- Modular monolith.
- Domain modules.
- Layered request flow for normal operations.
- Selective use-case folders for complex operations.
- Redis-backed workers later for heavy asynchronous work.
- Separate HTTP services only when independent synchronous scaling or runtime isolation is genuinely required.

Standard request flow:

Route
  -> Middleware
  -> Controller
  -> Service
  -> Repository
  -> Prisma / Supabase / Redis

Responsibility split:
- Supabase Auth: login, passwords, access tokens, refresh tokens, authenticated user identity.
- Prisma: PostgreSQL models, migrations, repositories, transactions, and application data.
- Zod: runtime validation for environment variables and HTTP request bodies.
- CASL: authorization rules later, before organizations/incidents/tasks are fully implemented.
- Redis: short-lived caches, rate limits, queues, locks, and workers later.
- PostgreSQL: permanent source of truth and data-integrity constraints.

Authentication and authorization roadmap
-----------------------------------------
Phase 1:
- Supabase Auth + Prisma + simple Express middleware.
- First protected role: active SUPER_ADMIN.

Phase 2:
- Add @casl/ability and @casl/prisma before implementing the main domain modules.
- Add ability.middleware.ts and authorize.middleware.ts.
- Enforce both route-level and record-level authorization.

Phase 3:
- Add Redis caching for profile, membership, and permission-building data.
- PostgreSQL remains the source of truth.
- Invalidate authorization cache immediately after role, membership, account, or organization status changes.

STEP 5 — Configure the dedicated Prisma database role and connection
================================================================

EcoTrack uses a dedicated PostgreSQL role for Prisma instead of exposing owner credentials.

Run through the Supabase SQL Editor with a strong private password:

CREATE USER "prisma"
WITH PASSWORD 'REPLACE_WITH_A_STRONG_PRIVATE_PASSWORD'
BYPASSRLS
CREATEDB;

GRANT "prisma" TO "postgres";

GRANT USAGE ON SCHEMA public TO prisma;
GRANT CREATE ON SCHEMA public TO prisma;

GRANT ALL ON ALL TABLES IN SCHEMA public TO prisma;
GRANT ALL ON ALL ROUTINES IN SCHEMA public TO prisma;
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO prisma;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres
IN SCHEMA public
GRANT ALL ON TABLES TO prisma;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres
IN SCHEMA public
GRANT ALL ON ROUTINES TO prisma;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres
IN SCHEMA public
GRANT ALL ON SEQUENCES TO prisma;

Connection requirements:
- Use the Supabase Session Pooler on port 5432 for the current setup.
- Username format may include the project reference:
  prisma.PROJECT_REF
- Keep DATABASE_URL only in backend/.env.
- Never put the database URL in web/ or mobile/.
- Never commit backend/.env.

Prisma can execute migration SQL that creates tables, indexes, functions, and triggers
when the role has sufficient privileges. PostgreSQL/Supabase-specific SQL should be kept
inside reviewed Prisma migration.sql files. Do not modify Supabase-managed auth, storage,
or vault schemas through Prisma.

STEP 10 — Define the initial Prisma schema
================================================================

Location:
backend/prisma/schema.prisma

Canonical content:

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

enum PlatformRole {
  USER
  SUPER_ADMIN
}

enum AccountStatus {
  ACTIVE
  SUSPENDED
}

enum OrganizationStatus {
  ACTIVE
  SUSPENDED
}

enum OrganizationRole {
  MEMBER
  VOLUNTEER
  ORG_ADMIN
}

enum MembershipStatus {
  INVITED
  ACTIVE
  SUSPENDED
}

model UserProfile {
  id         String @id @default(uuid()) @db.Uuid
  authUserId String @unique @map("auth_user_id") @db.Uuid

  email    String @unique
  fullName String @map("full_name")

  platformRole PlatformRole  @default(USER) @map("platform_role")
  status       AccountStatus @default(ACTIVE)

  memberships OrganizationMember[]

  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  @@index([platformRole, status])
  @@map("user_profiles")
}

model Organization {
  id String @id @default(uuid()) @db.Uuid

  name String
  slug String @unique

  description  String?
  contactEmail String? @map("contact_email")

  status OrganizationStatus @default(ACTIVE)

  memberships OrganizationMember[]

  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  @@index([status])
  @@map("organizations")
}

model OrganizationMember {
  id String @id @default(uuid()) @db.Uuid

  organizationId String @map("organization_id") @db.Uuid
  userId         String @map("user_id") @db.Uuid

  role   OrganizationRole @default(MEMBER)
  status MembershipStatus @default(ACTIVE)

  organization Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  user         UserProfile  @relation(fields: [userId], references: [id], onDelete: Cascade)

  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  @@unique([organizationId, userId])
  @@index([userId, status])
  @@index([organizationId, role, status])
  @@map("organization_members")
}

Validate:

npx prisma format
npx prisma validate

Important model decisions:
- UserProfile.id is EcoTrack's internal profile ID.
- UserProfile.authUserId stores the Supabase auth.users.id UUID.
- Platform role and organization role are separate.
- One user can belong to several organizations with different roles.
- Citizen/basic-user capability is not stored as an organization role.
- Do not add all future domain tables before the foundation is working.

STEP 13 — Create and apply the first migrations, including RLS
================================================================

Initial migration name:
init_identity_and_tenancy

Preferred safe workflow:

npm run prisma:migrate -- --name init_identity_and_tenancy --create-only

Review:
backend/prisma/migrations/<timestamp>_init_identity_and_tenancy/migration.sql

Apply:
npm run prisma:migrate

Then regenerate:
npm run prisma:generate

Check:
npx prisma migrate status

The first migration creates:
- PostgreSQL enums.
- public.user_profiles.
- public.organizations.
- public.organization_members.
- Foreign keys, unique constraints, and indexes.
- _prisma_migrations history table.

RLS and direct Data API blocking
--------------------------------
Add RLS/security changes as custom migration SQL:

ALTER TABLE "public"."user_profiles"
ENABLE ROW LEVEL SECURITY;

ALTER TABLE "public"."organizations"
ENABLE ROW LEVEL SECURITY;

ALTER TABLE "public"."organization_members"
ENABLE ROW LEVEL SECURITY;

REVOKE ALL PRIVILEGES
ON TABLE "public"."user_profiles"
FROM anon, authenticated;

REVOKE ALL PRIVILEGES
ON TABLE "public"."organizations"
FROM anon, authenticated;

REVOKE ALL PRIVILEGES
ON TABLE "public"."organization_members"
FROM anon, authenticated;

Meaning:
- RLS controls which rows a database role may access when policies exist.
- With RLS enabled and no policies, normal direct access is denied by default.
- REVOKE removes table-level privileges from Supabase anon and authenticated Data API roles.
- Web/mobile clients therefore cannot directly query these tables using supabase.from(...).
- EcoTrack frontends call the Express backend.
- The privileged backend Prisma role has table permissions and BYPASSRLS.
- RLS and REVOKE do not prevent the database owner from creating tables through Supabase.
- They apply to access on the specified tables.

Important migration correction
------------------------------
An applied migration must never be edited afterward.

If an already-applied migration was modified:
1. Restore that migration.sql exactly to the version originally applied.
2. Create a new later migration folder containing the added RLS SQL.
3. Apply the new pending migration.
4. Do not run prisma migrate reset against valuable data merely to fix an edited migration.

Current known migration:
20260727094824_init_identity_and_tenancy

RLS should therefore exist in a later migration, for example:
<later_timestamp>_enable_rls/migration.sql

Verify RLS through Supabase SQL Editor:

SELECT
  schemaname,
  tablename,
  rowsecurity
FROM pg_tables
WHERE schemaname = 'public'
  AND tablename IN (
    'user_profiles',
    'organizations',
    'organization_members'
  )
ORDER BY tablename;

Expected rowsecurity:
true for all three tables.

STEP 14 — Create the first Supabase Auth user and seed SUPER_ADMIN
================================================================

Supabase Dashboard:
Authentication
  -> Users
  -> Add user

Use:
- An email address you control.
- A strong password.
- Auto-confirm when appropriate for the development user.

Copy:
auth.users.id UUID

Update backend/.env:

SUPER_ADMIN_AUTH_USER_ID="COPIED_AUTH_USER_UUID"
SUPER_ADMIN_EMAIL="THE_SAME_EMAIL_USED_IN_SUPABASE_AUTH"
SUPER_ADMIN_FULL_NAME="EcoTrack Super Admin"

Do not:
- Insert directly into auth.users.
- Put the password in seed.ts.
- Confuse auth.users.id with UserProfile.id.

Create:
backend/prisma/seed.ts

Content:

import { env } from "../src/config/env.js";
import { prisma } from "../src/database/prisma.js";
import {
  AccountStatus,
  PlatformRole,
} from "../src/generated/prisma/enums.js";

async function main(): Promise<void> {
  const authUserId = env.SUPER_ADMIN_AUTH_USER_ID.trim();
  const email = env.SUPER_ADMIN_EMAIL.trim().toLowerCase();
  const fullName = env.SUPER_ADMIN_FULL_NAME.trim();

  if (!authUserId) {
    throw new Error(
      "SUPER_ADMIN_AUTH_USER_ID is empty. Create the Supabase Auth user and copy its UUID into backend/.env.",
    );
  }

  const existingProfileWithEmail =
    await prisma.userProfile.findUnique({
      where: {
        email,
      },
      select: {
        id: true,
        authUserId: true,
      },
    });

  if (
    existingProfileWithEmail &&
    existingProfileWithEmail.authUserId !== authUserId
  ) {
    throw new Error(
      `A user profile with email "${email}" already exists but uses a different authUserId.`,
    );
  }

  const superAdminProfile = await prisma.userProfile.upsert({
    where: {
      authUserId,
    },

    update: {
      email,
      fullName,
      platformRole: PlatformRole.SUPER_ADMIN,
      status: AccountStatus.ACTIVE,
    },

    create: {
      authUserId,
      email,
      fullName,
      platformRole: PlatformRole.SUPER_ADMIN,
      status: AccountStatus.ACTIVE,
    },

    select: {
      id: true,
      authUserId: true,
      email: true,
      fullName: true,
      platformRole: true,
      status: true,
      createdAt: true,
      updatedAt: true,
    },
  });

  console.log("EcoTrack super-admin profile is ready:");

  console.log(
    JSON.stringify(
      superAdminProfile,
      null,
      2,
    ),
  );
}

main()
  .catch((error: unknown) => {
    console.error("EcoTrack database seed failed:");
    console.error(error);

    process.exitCode = 1;
  })
  .finally(async () => {
    await prisma.$disconnect();
  });

Run:
npm run prisma:seed

Why upsert:
- First run creates the profile.
- Later runs update the same profile.
- It avoids duplicate SUPER_ADMIN records.

The first platform super admin does not need an organization_members row yet.

STEP 16 — Create the backend Supabase Auth client
================================================================

Location:
backend/src/config/supabase.ts

Content:

import { createClient } from "@supabase/supabase-js";

import { env } from "./env.js";

export const supabaseAuth = createClient(
  env.SUPABASE_URL,
  env.SUPABASE_PUBLISHABLE_KEY,
  {
    auth: {
      autoRefreshToken: false,
      persistSession: false,
      detectSessionInUrl: false,
    },
  },
);

Purpose:
- Create one reusable server-side Supabase Auth client.
- Later auth.middleware.ts uses:
  supabaseAuth.auth.getUser(accessToken)

Meaning of auth options:
- autoRefreshToken: false
  The Express backend does not own and refresh each frontend user's session.
- persistSession: false
  The shared server client must not store browser-style sessions.
- detectSessionInUrl: false
  The backend does not inspect browser callback URLs for OAuth, magic links,
  email confirmation, invitation, or password-reset results.

Frontend responsibility:
- Perform login.
- Store/manage the user's session appropriately.
- Refresh access tokens.
- Process browser/mobile authentication redirects when used.

Backend responsibility:
- Receive Authorization: Bearer <access-token>.
- Verify the access token for every protected request.
- Public routes such as /health do not require token verification.

This client does not replace Prisma:
- Supabase Auth client verifies identity.
- Prisma reads user_profiles, roles, organizations, and memberships.

import { prisma } from "../database/prisma.js";

type ConnectionInformation = {
  databaseName: string;
  schemaName: string;
  databaseUser: string;
};

async function checkDatabase(): Promise<void> {
  console.log("Checking EcoTrack database connection...");

  const connectionInformation =
    await prisma.$queryRaw<ConnectionInformation[]>`
      SELECT
        current_database() AS "databaseName",
        current_schema() AS "schemaName",
        current_user AS "databaseUser"
    `;

  const currentConnection = connectionInformation[0];

  if (!currentConnection) {
    throw new Error(
      "PostgreSQL connected but did not return connection information.",
    );
  }

  const [
    userProfileCount,
    organizationCount,
    organizationMemberCount,
  ] = await Promise.all([
    prisma.userProfile.count(),
    prisma.organization.count(),
    prisma.organizationMember.count(),
  ]);

  console.log("EcoTrack database connection succeeded.");
  console.log("");
  console.log(`Database: ${currentConnection.databaseName}`);
  console.log(`Schema: ${currentConnection.schemaName}`);
  console.log(`Database user: ${currentConnection.databaseUser}`);
  console.log("");
  console.log("Current table records:");
  console.log(`User profiles: ${userProfileCount}`);
  console.log(`Organizations: ${organizationCount}`);
  console.log(
    `Organization memberships: ${organizationMemberCount}`,
  );
}

checkDatabase()
  .catch((error: unknown) => {
    console.error("EcoTrack database check failed:");

    if (error instanceof Error) {
      console.error(error.message);
    } else {
      console.error(error);
    }

    process.exitCode = 1;
  })
  .finally(async () => {
    await prisma.$disconnect();
  });

Responsibilities:
- Route: endpoint and middleware chain.
- Middleware: authentication, tenant context, ability, authorization.
- Zod schema: validate untrusted HTTP input at runtime.
- Controller: translate HTTP request to service call and return response.
- Service/use case: business rules, orchestration, transactions.
- Repository: Prisma queries, tenant filters, reusable selects.
- Prisma: permanent PostgreSQL data.
- Supabase Auth: identity and sessions.
- Supabase Storage later: files/images.
- Redis later: caches, queues, locks, temporary state.

Tenant-security rule:
Every organization-owned record query must include the authorized organizationId
derived from trusted backend membership context.

Correct:
where: {
  id: taskId,
  organizationId: authorizedOrganizationId
}

Incorrect:
where: {
  id: taskId
}

Do not trust:
- A role sent by the frontend.
- An organization ID without membership verification.
- Hidden frontend buttons as authorization.
- Cached permission data after a known role/status change.
