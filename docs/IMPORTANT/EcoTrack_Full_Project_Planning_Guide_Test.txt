1. Project Understanding
The proposed project is an EcoTrack platform for community-driven environmental incident reporting and cleanup
coordination. Citizens report environmental problems such as illegal dumping, water pollution, blocked drainage, or
unsafe waste areas using a mobile application. Organization administrators verify these reports, convert valid reports
into cleanup tasks or events, assign volunteers, and track progress through a web dashboard.
The system is designed as a Software-as-a-Service platform. This means multiple independent environmental
organizations can use the same platform while keeping their data separated. For example, a lake protection group, a
coastal cleanup group, and a university green club can all use the same system, but each organization sees only its
own reports, volunteers, tasks, and dashboards.
1.1 Main Problem
- Environmental reports are currently scattered across social media groups, phone calls, paper notes, and messaging
apps.
- Useful reports can be lost in long chat threads.
- Community groups struggle to verify reports and convert them into real cleanup actions.
- There is no clear record of who was assigned, what happened, when a cleanup was completed, and what impact
was achieved.
- Existing environmental management systems can be too complex, expensive, or government-focused for small local
organizations.
1.2 Proposed Solution in Simple Words
EcoTrack will act as a shared digital workspace for environmental organizations. The public can submit geo-tagged
incident reports with photos. Administrators can review, verify, assign, and monitor work. Volunteers can view
assigned cleanup tasks and update progress. The platform stores all activity in a structured, searchable, and
auditable way.

2. What Makes This Project Special
The project should not be presented as only a simple reporting app. It should be presented as a scalable SaaS
coordination platform for environmental organizations. The strongest speciality is software architecture and practical
deployment readiness.
2.1 Speciality 1 - Multi-Tenant SaaS
Multiple organizations can use the same backend and database, while tenant isolation ensures each organization
only accesses its own data. This is more advanced than a single NGO app.
- Each incident belongs to one organization.

2.2 Speciality 2 - Geospatial Incident and Task Coordination
Incidents are not just text records. They are location-based environmental events. The platform should use maps,
coordinates, and location filtering to support practical cleanup planning.
- Citizens mark incident location on a map or use current GPS location.
- Admins can view incidents on a map and filter by category, status, severity, and region.
- Volunteers can view nearby or assigned tasks.
- Future analytics can show incident density and cleanup impact by area.
2.3 Speciality 3 - Low-Bandwidth and Low-End Device Support
This is important for community users. Redis does not run on low-power phones. Redis runs on the server.
Low-end-device support should be achieved through careful mobile design and efficient backend responses.
- Compress photos before upload.
- Use offline report drafts, so a user can prepare a report even with weak internet.
- Use retry upload when connectivity returns.
- Use pagination and small API responses.
- Cache frequently used data on the mobile app where suitable.
- Use Redis on the server to make dashboard and map queries faster.
2.4 Speciality 4 - Configurable Workflows
Different organizations may use different reporting and cleanup processes. Instead of hardcoding statuses, allow
organization admins to configure status stages.
Example workflow 1:
Reported -> Verified -> Cleanup Scheduled -> In Progress -> Resolved
Example workflow 2:
New -> Under Review -> Assigned -> Completed -> Closed
2.5 Speciality 5 - DevOps and Industry Practices
CI/CD, Docker, automated testing, API documentation, and Redis are not extra decoration. They show that the group
understands modern software engineering practice and can build a system that is maintainable and deployable.

processing, and Docker with GitHub Actions will support CI/CD-based deployment.

8.1 Multi-Tenant Isolation Rule
Every API request must know the authenticated user's organization_id. The backend must automatically filter
tenant-owned data by organization_id. The frontend should not be trusted to send organization_id for
security-sensitive filtering.
Example rule:
Admin from Organization A requests /api/incidents
Backend returns only incidents where incidents.organization_id = admin.organization_id
Never allow:
Admin from Organization A directly accessing Organization B incident by changing URL id

19. What Not to Do
- Do not describe the project as only a garbage reporting app.
- Do not promise AI, IoT, satellite analysis, or payments unless the group is really going to build them.
- Do not use NestJS if the team is not ready for its learning curve.
- Do not put all backend code in one large file. Keep modules separated.
- Do not skip tenant isolation testing. Multi-tenancy is the project's main speciality.
- Do not add advanced features before the MVP demo flow works.
20. Final Recommended Scope for the 3-Member Group
The best final scope is:
Mobile app for citizens and volunteers + React TypeScript web dashboard for admins + Express
TypeScript backend with PostgreSQL/PostGIS, Redis, file storage, role-based access, multi-tenant
isolation, configurable workflows, basic analytics, CI/CD, and Dockerized deployment.
This scope is strong enough for a Software Engineering Project because it includes a real working product, separate
modules for individual evaluation, proper software engineering design, industry technologies, deployment practices,
and a measurable evaluation plan.
