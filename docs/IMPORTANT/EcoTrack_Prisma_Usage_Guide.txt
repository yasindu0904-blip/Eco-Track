EcoTrack Prisma Usage Guide
===========================

Purpose
-------
This document records how Prisma should be used in EcoTrack.

1. Prisma's Responsibility
--------------------------
Prisma is EcoTrack's ORM and database access layer.

Use Prisma for:
- Defining PostgreSQL models and relations
- Migrations
- Type-safe queries
- CRUD operations
- Relation queries
- Transactions
- Filtering and sorting
- Pagination
- Aggregations
- Seed data
- Repository-layer code
- Selected raw SQL and PostGIS queries

Prisma is not:
- Authentication
- JWT creation
- Authorization by itself
- Caching
- A background queue

EcoTrack responsibility split:

Supabase Auth
- Login and signup
- Password handling
- Access and refresh tokens
- Authenticated Supabase user ID

Authorization
- auth.middleware.ts
- tenant.middleware.ts
- permission middleware
- Optional CASL authorization rules

Prisma
- User profiles
- Organizations
- Memberships
- Incidents
- Tasks
- Assignments
- Workflows
- Notifications
- Audit records

Redis
- Cache
- Rate limits
- Queues
- Locks
- Temporary counters and coordination

2. Recommended Location
-----------------------
backend/
├── prisma/
│   ├── schema.prisma
│   ├── migrations/
│   └── seed.ts
└── src/
    ├── database/
    │   └── prisma.ts
    └── modules/
        ├── users/repositories/user.repository.ts
        ├── organizations/repositories/organization.repository.ts
        ├── incidents/repositories/incident.repository.ts
        └── tasks/repositories/task.repository.ts

Preferred flow:

Route
  -> Middleware
  -> Controller
  -> Service
  -> Repository
  -> Prisma

Controllers should not normally call Prisma directly.

3. Database Models
------------------
Use schema.prisma to define:
- Models
- Fields
- PostgreSQL types
- Primary keys
- Unique constraints
- Foreign keys
- Relations
- Enums
- Indexes
- Defaults
- Delete behavior

Main EcoTrack models:
- UserProfile
- Organization
- OrganizationMember
- Incident
- IncidentPhoto
- Task
- TaskAssignment
- WorkflowStatus
- StatusHistory
- Notification
- UserDevice
- AuditLog

4. CRUD
-------
Useful Prisma methods:
- create
- createMany
- findUnique
- findUniqueOrThrow
- findFirst
- findMany
- update
- updateMany
- upsert
- delete
- deleteMany
- count

EcoTrack examples:
- Create an organization
- Find a profile using authUserId
- List incidents for an organization
- Update a task status
- Upsert an Expo device token
- Count active volunteers

5. Select Only Needed Fields
----------------------------
Use select to return only necessary data.

Benefits:
- Smaller responses
- Less database work
- Lower data exposure
- Better mobile performance

Examples:
- User ID, name, and role only
- Incident summary without full history
- Volunteer name and availability only

6. Relations
------------
Use include or nested select for:
- User and organization memberships
- Incident and photos
- Task, incident, and assignments
- Organization and active admins
- Workflow and ordered statuses

Avoid loading large relation trees when the endpoint does not need them.

7. Tenant Filtering
-------------------
Every organization-owned query must include organizationId.

Correct:

where: {
  id: taskId,
  organizationId: authorizedOrganizationId
}

Incorrect:

where: {
  id: taskId
}

authorizedOrganizationId must come from verified backend membership context, not from a trusted frontend role.

8. Filtering and Sorting
------------------------
Use where and orderBy.

Useful incident filters:
- status
- severity
- category
- date range
- reporter
- region

Useful task filters:
- status
- scheduled date
- assigned volunteer

Useful sorting:
- newest report first
- highest severity first
- nearest scheduled task first
- alphabetical volunteer list

9. Pagination
-------------
Use offset pagination for small web tables:
- skip
- take

Use cursor pagination for large or infinite lists:
- cursor
- take
- orderBy

Recommended:
- Web admin table: offset pagination initially
- Mobile feed: cursor pagination as data grows

Use stable ordering such as createdAt and id.

10. Search
----------
Use string filters:
- contains
- startsWith
- endsWith
- mode: "insensitive"

Search examples:
- Incident title
- Incident description
- User full name
- Organization name
- Task title

11. Nested Writes
-----------------
Use nested writes for related records.

Examples:
- Create organization and first admin membership
- Create incident and photo metadata
- Create task and initial status history
- Create notification with related metadata

12. Transactions
----------------
Use transactions when all operations must succeed or fail together.

EcoTrack examples:
- Organization + creator membership + audit log
- Verify incident + status history + audit log
- Create task + link incident + status history
- Assign volunteers + assignments + notification records
- Complete task + close incident + audit log

Use:
- Nested writes
- prisma.$transaction([...])
- Interactive transactions

Do not keep a database transaction open while:
- Sending Expo notifications
- Uploading images
- Calling external HTTP services
- Waiting for workers

Correct pattern:
1. Save database state in transaction
2. Commit
3. Queue external work

13. Bulk Operations
-------------------
Use:
- createMany
- updateMany
- deleteMany

Examples:
- Add several task assignments
- Mark many notifications read
- Suspend memberships of a disabled organization
- Insert default workflow statuses

14. Upsert
----------
Use upsert when a record may already exist.

Examples:
- User profile provisioning
- Expo device token registration
- Organization settings
- Notification preferences

15. Aggregations
----------------
Use:
- count
- aggregate
- groupBy
- distinct

Dashboard examples:
- Pending incident count
- Active task count
- Volunteer count
- Incidents grouped by category
- Tasks grouped by status
- Monthly cleanup totals

Cache expensive repeated dashboard results with Redis later.

16. Constraints and Indexes
---------------------------
Likely constraints and indexes:
- UserProfile.authUserId unique
- Organization.slug unique
- OrganizationMember [organizationId, userId] unique
- Incident [organizationId, status, createdAt]
- Incident [organizationId, category]
- Task [organizationId, status, scheduledAt]
- TaskAssignment [taskId, volunteerId] unique
- Notification [userId, readAt, createdAt]

Database constraints protect data even if application code contains a bug.

17. Enums
---------
Use enums for stable values:
- PlatformRole
- MembershipRole
- AccountStatus
- MembershipStatus
- NotificationType

For configurable organization workflows, use workflow tables rather than hardcoding every status in Prisma enums.

18. Soft Delete
---------------
Use fields such as:
- deletedAt
- archivedAt
- status = INACTIVE

Likely soft-delete candidates:
- Organizations
- User profiles
- Incidents
- Tasks
- Memberships

Repositories must consistently exclude archived records.

19. Repository Pattern
----------------------
Repository responsibilities:
- Prisma queries
- Tenant filters
- Reusable select/include definitions
- Persistence details

Service responsibilities:
- Business rules
- Transactions
- Calling multiple repositories
- Queuing work after commit

20. Reusable Select Objects
---------------------------
Useful shared selections:
- publicUserSelect
- membershipSelect
- incidentSummarySelect
- taskDetailsSelect

This prevents repeated query definitions and accidental exposure.

21. Generated Types
-------------------
Prisma generates TypeScript types for:
- Models
- Query filters
- Create/update inputs
- Transaction clients
- Select/include payloads

Do not manually duplicate every database type.

Keep API request types separate because external input still needs runtime validation.

22. Runtime Validation
----------------------
Prisma type safety does not validate incoming HTTP JSON.

Use Zod first:

Request body
  -> Zod
  -> Authorized service input
  -> Prisma

23. Error Handling
------------------
Map Prisma errors to API errors:
- Unique constraint -> 409 Conflict
- Missing record -> 404 Not Found
- Foreign-key failure -> 400 or 409
- Database unavailable -> 503
- Invalid request -> 400

Do not send raw database errors to the frontend.

24. Migrations
--------------
Use Prisma Migrate for schema changes.

Rules:
- Use meaningful migration names
- Review generated SQL
- Do not casually change old applied migrations
- Test required-column changes
- Back up before risky production migrations

25. Seed Data
-------------
Use seed.ts for:
- Default platform settings
- Demo organization
- Default workflow statuses
- Incident categories
- Severity definitions
- Development memberships

Do not store passwords in seed files.

26. Prisma Studio
-----------------
Use Prisma Studio for:
- Inspecting records
- Checking relations
- Confirming seed data
- Debugging migrations
- Verifying memberships and roles

It is not the production admin interface.

27. Raw SQL and PostGIS
-----------------------
Use normal Prisma queries first.

Use parameterized raw SQL or TypedSQL for:
- PostGIS ST_DWithin
- PostGIS ST_Distance
- Nearby incident search
- Spatial bounding boxes
- Heatmap aggregation
- Specialized full-text search
- Highly optimized analytics

Keep geospatial SQL in:
incidents/repositories/incidentGeo.repository.ts

Avoid unsafe raw queries with user input.

28. Client Extensions
---------------------
Prisma Client extensions can add:
- Custom model methods
- Query interception
- Result fields
- Request-specific clients
- Logging context
- Soft-delete behavior
- Authorization-aware behavior

Do not hide tenant rules so deeply that they become difficult to test.

29. Authorization-Aware Prisma Queries
--------------------------------------
Prisma is not the authorization engine.

Recommended architecture:
- Supabase Auth verifies identity
- CASL defines permitted actions and conditions
- @casl/prisma can convert permission conditions into Prisma filters
- Repository combines permission filters with organization filters

Even with CASL, test cross-tenant access carefully.

30. Logging
-----------
Prisma can log:
- Queries
- Errors
- Warnings
- Query duration

Rules:
- Do not log secrets
- Avoid noisy production logs
- Add request IDs
- Monitor slow queries

31. Connection Management
-------------------------
Create one Prisma client singleton per backend process.

Do not create a new PrismaClient per request.

Each worker process may have its own singleton.

32. Testing
-----------
Test:
- Tenant filtering
- Role and membership conditions
- Transaction rollback
- Unique constraints
- Pagination
- Soft-delete filtering
- Cross-organization access denial
- Status transitions

Always create Organization A and Organization B test data.

33. Audit Logs
--------------
Use transactions to save audit logs with:
- Organization creation
- Admin assignment
- Incident verification or rejection
- Task creation
- Volunteer assignment
- Task completion
- Incident closure
- User suspension

34. Optimistic Concurrency
--------------------------
Use updatedAt, a version field, or conditional updateMany.

Example:
Update a task only when its current status is ASSIGNED.

This prevents conflicting simultaneous updates.

35. Idempotency
---------------
Use unique constraints and upsert for retry-safe work.

Examples:
- One device token registration
- One assignment per task and volunteer
- One processed external event
- One completion submission per request ID

Redis can hold short-lived idempotency state; PostgreSQL constraints provide permanent protection.

36. Performance Rules
---------------------
- Select only required fields
- Add indexes based on real queries
- Paginate lists
- Avoid huge include trees
- Avoid Prisma queries inside loops
- Use createMany for bulk inserts
- Use transactions for related changes
- Cache repeated expensive results in Redis
- Use raw SQL only when justified
- Measure before optimizing

Final Rule
----------
Use Prisma as EcoTrack's type-safe database layer.

Use Supabase Auth for identity.

Use middleware or CASL for authorization.

Use Zod for request validation.

Use Redis for caching, queues, and workers.

Use PostgreSQL constraints and indexes for final data integrity.
