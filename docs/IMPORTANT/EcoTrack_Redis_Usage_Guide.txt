EcoTrack Redis Usage Guide
==========================

Purpose
-------
This file records the useful Redis features that can strengthen EcoTrack without turning the project into an unnecessarily complex system.

Important Principle
-------------------
Redis runs on the backend infrastructure, not on citizen or volunteer mobile phones.

Redis should be used only when it provides a clear benefit such as:

- Faster responses
- Lower database load
- Better rate limiting
- Background job processing
- Short-lived session or role caching
- Reliable retryable work
- Temporary coordination between processes

Do not use Redis as the main permanent database.

1. Organization Membership and Role Cache
-----------------------------------------
Problem:
Every protected request may query organization_members to check whether the user belongs to the organization and what role the user has.

Redis use:
Cache the membership result for a short time.

Example key:
membership:{userId}:{organizationId}

Example value:
{
  "role": "ORG_ADMIN",
  "status": "ACTIVE"
}

Suggested expiry:
3 to 5 minutes

Benefit:
- Faster authorization checks
- Lower PostgreSQL load
- Useful when many API requests arrive from the same logged-in user

Important:
When an admin changes a user's role or membership status, delete the related Redis key immediately.

2. User Profile and Workspace Cache
-----------------------------------
Problem:
After login, the frontend needs the user profile, platform role, and organization memberships.

Redis use:
Cache the result returned by GET /api/auth/me.

Example key:
user-context:{userId}

Possible contents:
- User profile
- Platform role
- Joined organizations
- Role inside each organization
- Account status

Suggested expiry:
3 to 5 minutes

Benefit:
- Faster login initialization
- Faster workspace switching
- Lower repeated database reads

Important:
Invalidate this cache after role changes, membership changes, account suspension, or profile updates.

3. Super-Admin and Organization Dashboard Cache
-----------------------------------------------
Problem:
Dashboard statistics may run several COUNT, GROUP BY, and aggregate queries.

Redis use:
Cache dashboard results.

Example keys:
dashboard:platform
dashboard:organization:{organizationId}

Possible cached values:
- Pending incident count
- Verified incident count
- Active task count
- Resolved incident count
- Volunteer count
- Reports by category
- Cleanups by month

Suggested expiry:
30 seconds to 2 minutes

Benefit:
- Faster dashboard loading
- Lower database load
- Good feature for demonstrating measurable performance improvement

Invalidation:
Delete the relevant dashboard cache when incidents, tasks, volunteers, or organizations change.

4. Nearby Incident and Map Query Cache
--------------------------------------
Problem:
PostGIS nearby and map-area queries can become expensive when many users request similar areas.

Redis use:
Cache nearby-query results for a short time.

Example key:
nearby-incidents:{organizationId}:{latBucket}:{lngBucket}:{radius}:{filtersHash}

Suggested expiry:
30 to 90 seconds

Benefit:
- Faster map loading
- Lower PostGIS query load
- Better performance for high-traffic map areas

Important:
Round or bucket latitude and longitude so tiny coordinate differences do not create endless keys.

5. API Rate Limiting
--------------------
Problem:
Attackers or malfunctioning clients may repeatedly call login or incident-report endpoints.

Redis use:
Count requests within a time window.

Example keys:
rate-limit:login:{ipAddress}
rate-limit:report:{userId}
rate-limit:password-reset:{emailHash}

Possible policies:
- Limit login attempts per minute
- Limit incident submissions per hour
- Limit photo uploads per minute
- Limit notification token changes per hour

Benefit:
- Reduces brute-force login attempts
- Reduces spam reports
- Protects storage and backend resources

6. Duplicate Incident Submission Protection
-------------------------------------------
Problem:
A slow mobile connection may cause the user to press Submit multiple times.

Redis use:
Create a short-lived idempotency key.

Example key:
idempotency:{userId}:{requestId}

Suggested expiry:
5 to 30 minutes

Flow:
1. Mobile sends an Idempotency-Key header.
2. Backend checks Redis.
3. If the key exists, return the previous result or reject the duplicate.
4. Otherwise process the report and save the result under the key.

Benefit:
- Prevents duplicate incident records
- Helps low-bandwidth retry behavior
- Makes mobile submission safer

7. Notification Queue
---------------------
Problem:
Assigning many volunteers may require many push notifications. Sending them inside the API request makes the request slow and less reliable.

Redis use:
Use a queue system backed by Redis.

Possible jobs:
- TASK_ASSIGNED
- REPORT_STATUS_CHANGED
- TASK_REMINDER
- INCIDENT_VERIFIED
- CLEANUP_COMPLETED

Flow:
API
  -> Save task assignment
  -> Save notification record
  -> Add notification job
  -> Return response

Notification worker
  -> Receive job
  -> Send Expo push notification
  -> Retry temporary failures
  -> Record result

Benefit:
- Fast API responses
- Retry handling
- Better reliability
- Worker can scale separately

8. Image-Processing Queue
-------------------------
Problem:
Resizing, thumbnail creation, metadata removal, and image optimization may be slow.

Redis use:
Queue image-processing jobs after the original image is stored.

Possible jobs:
- Resize large image
- Generate thumbnail
- Remove EXIF metadata
- Validate file format
- Compress dashboard version

Benefit:
- Upload API can respond quickly
- Heavy image work runs separately
- Failed jobs can retry

MVP note:
This is optional. First compress images on the mobile app and upload to Supabase Storage.

9. Export and Report-Generation Queue
-------------------------------------
Problem:
Generating a large PDF or CSV report may take several seconds or minutes.

Redis use:
Queue export jobs.

Flow:
1. Admin requests export.
2. API creates an export record with status QUEUED.
3. API adds the job to Redis.
4. Worker generates the file.
5. Worker saves the file URL and marks the job COMPLETED.
6. Admin receives a notification or sees the ready file.

Benefit:
- Avoids request timeout
- Reliable retries
- Large reports can be processed separately

10. Analytics Recalculation Queue
---------------------------------
Problem:
Detailed analytics may require expensive aggregate queries.

Redis use:
Queue recalculation jobs and cache the calculated result.

Possible triggers:
- Incident status changed
- Task completed
- Organization dashboard requested
- Scheduled nightly refresh

Benefit:
- Dashboard reads precomputed results
- Expensive calculations do not block normal API traffic

MVP note:
Use direct PostgreSQL queries first. Add this only if analytics becomes slow.

11. Scheduled Reminders
-----------------------
Problem:
Volunteers may need reminders before a cleanup task or when a task remains incomplete.

Redis use:
Use delayed queue jobs.

Examples:
- Reminder 24 hours before cleanup
- Reminder 2 hours before cleanup
- Follow-up when an assigned task is not accepted
- Reminder when completion evidence is missing

Benefit:
- Reliable delayed execution
- Worker handles delivery
- Avoids manual scheduler logic inside API routes

12. Temporary Verification Data
-------------------------------
Redis can store short-lived values such as:
- Organization invitation state
- Sensitive-action confirmation codes
- Temporary challenge data

Suggested expiry:
5 to 15 minutes

Important:
Supabase Auth already handles many authentication flows. Do not recreate Supabase authentication unnecessarily.

13. Organization Invitation Cache
---------------------------------
Example key:
organization-invite:{tokenHash}

Possible contents:
- organizationId
- intendedRole
- invitedEmail
- expiry
- maximumUses

Benefit:
- Fast validation
- Automatic expiry
- Easy one-time-use control

Permanent invitation history should remain in PostgreSQL when auditing is required.

14. Token Revocation or Logout Denylist
---------------------------------------
Redis can store revoked token identifiers until their normal expiry.

Example key:
revoked-token:{jti}

Use cases:
- Super admin suspends a user
- Password compromise
- Forced logout from all devices
- Security incident

MVP note:
Supabase session management may be enough initially. Add a denylist only when immediate revocation is required.

15. Distributed Locks
---------------------
Problem:
Two workers or requests may try to perform the same sensitive operation at the same time.

Example keys:
lock:close-incident:{incidentId}
lock:generate-export:{exportId}
lock:rebuild-analytics:{organizationId}

Benefit:
- Prevents duplicate processing
- Prevents duplicate exports
- Coordinates multiple backend instances

Important:
Every lock must have an expiry.

16. Cache Stampede Protection
-----------------------------
When a popular cache key expires, many requests may hit PostgreSQL at once.

Redis can use a short refresh lock or stale-while-revalidate strategy.

Benefit:
- Prevents sudden database spikes
- Useful when the platform scales horizontally

Advanced feature:
Not required for the first MVP.

17. Temporary Upload State
--------------------------
Example key:
upload-progress:{uploadId}

Possible contents:
- percentage
- current stage
- error message
- temporary file reference

Benefit:
- Frontend can show progress
- Useful for image or export workers

Permanent file metadata must remain in PostgreSQL.

18. Presence or Online Status
-----------------------------
Example key:
presence:{userId}

Suggested expiry:
30 to 90 seconds

Benefit:
- Online/offline indicator
- Can support future live features

Advanced feature:
Not needed for the current MVP.

19. WebSocket Pub/Sub
---------------------
Redis Pub/Sub can distribute live events across multiple backend instances.

Possible events:
- INCIDENT_CREATED
- TASK_UPDATED
- VOLUNTEER_ASSIGNED
- DASHBOARD_CHANGED

Important:
WebSockets are optional. REST plus polling and push notifications are enough for the MVP.

20. Search and Filter Cache
---------------------------
Example key:
incident-list:{organizationId}:{filtersHash}:{page}

Suggested expiry:
15 to 60 seconds

Benefit:
- Faster repeated searches
- Lower database load

Only cache common or expensive queries.

21. Device Delivery State
-------------------------
Permanent device records should remain in PostgreSQL.

Redis can temporarily hold:
- last-seen time
- delivery cooldown
- recent failed-delivery count

22. Retry and Failure Tracking
------------------------------
Redis-backed queues can provide:
- Automatic retry
- Exponential backoff
- Failed-job storage
- Attempt counts
- Delayed retry
- Dead-letter handling

Benefit:
- More reliable notifications and exports
- Failures do not block API requests

23. Event Deduplication
-----------------------
Example key:
processed-event:{eventId}

Benefit:
- Prevents duplicate notifications
- Prevents duplicate exports
- Prevents duplicate worker actions

24. Worker Health Monitoring
----------------------------
Workers can periodically update heartbeat keys.

Example keys:
worker-heartbeat:notifications
worker-heartbeat:images
worker-heartbeat:exports

Suggested expiry:
30 to 60 seconds

Benefit:
- Super-admin dashboard can show worker status
- Helps detect failed worker processes

25. Feature Flags and Temporary Configuration
---------------------------------------------
Permanent feature flags should remain in PostgreSQL.

Redis can cache flags such as:
- Enable image worker
- Enable heatmap
- Enable workflow customization
- Enable bulk notifications

Recommended Redis Priorities for EcoTrack
-----------------------------------------
Phase 1: Login and foundation
- No Redis required yet
- Build Supabase Auth, Prisma, profiles, roles, and middleware first

Phase 2: Core MVP
- Organization membership and role cache
- Basic rate limiting
- Dashboard cache
- Duplicate submission protection

Phase 3: Notifications
- Notification queue
- Delayed reminders
- Retry and failure tracking

Phase 4: Performance and advanced features
- Nearby incident cache
- Filtered list cache
- Export queue
- Analytics recalculation
- Distributed locks
- Worker heartbeat monitoring

Phase 5: Optional scale features
- WebSocket Pub/Sub
- Presence
- Cache stampede protection
- Advanced feature flags

Recommended Key Naming Style
----------------------------
Use a consistent prefix:

ecotrack:{environment}:{feature}:{identifier}

Examples:
ecotrack:dev:membership:user123:org456
ecotrack:dev:dashboard:organization:org456
ecotrack:dev:rate-limit:login:192.168.1.10
ecotrack:dev:idempotency:user123:request789
ecotrack:dev:worker-heartbeat:notifications

Cache Invalidation Rules
------------------------
Every cached value needs a clear invalidation rule.

Examples:
- Membership changed -> delete membership and user-context keys
- Incident created -> delete incident-list, nearby, and dashboard keys
- Task status changed -> delete task-list and dashboard keys
- Organization updated -> delete organization and user-context keys
- User suspended -> delete user-context and membership keys

Security Rules
--------------
- Never store plain passwords in Redis.
- Never treat Redis as permanent storage.
- Keep Redis private and inaccessible from the public internet.
- Use authentication and TLS in production when supported.
- Do not store unnecessary sensitive personal data.
- Use short expiries for authorization and session-related cache.
- Do not trust frontend-supplied roles.
- Protect Redis from unbounded key growth.

Observability
-------------
Useful measurements:
- Cache hit rate
- Cache miss rate
- Queue length
- Oldest waiting job
- Failed job count
- Worker heartbeat status
- Average job duration
- Rate-limit blocks
- Redis memory usage

Final Rule to Remember
----------------------
Use PostgreSQL for permanent truth.

Use Redis for fast temporary state, caching, queues, counters, locks, and coordination.

Add each Redis feature only when it solves a clear EcoTrack problem.
