EcoTrack - Simple Task Flow Diagrams
For group understanding

Purpose
This text file explains the EcoTrack system flow in a simple line-by-line style.
It is not a heavy architecture document. It is meant to help the group understand how mobile app, web app, backend, Supabase Auth, PostgreSQL/PostGIS, Redis, and Expo Push Notifications connect together.

============================================================
0. OVERALL SYSTEM IDEA
============================================================

One user account
    ↓
Can act as Citizen
    ↓
Can act as Volunteer in one or more organizations
    ↓
Can act as Organization Admin/Leader in one or more organizations
    ↓
Can act as Super Admin only if platform-level permission exists

Mobile App
    ↓
Used mainly by citizens and volunteers
    ↓
Report incidents, view own reports, view assigned tasks, receive notifications

Web App
    ↓
Used mainly by organization admins/leaders and super admins
    ↓
Verify reports, create tasks, assign volunteers, manage workflows, view analytics

Shared Backend API
    ↓
Used by both mobile app and web app
    ↓
Handles authentication, tenant checks, role checks, database operations, notifications

Supabase Auth
    ↓
Handles login/signup/invitation and gives JWT access token

Supabase PostgreSQL + PostGIS
    ↓
Stores organizations, users, reports, tasks, assignments, statuses, locations

Redis
    ↓
Caches role/membership checks, dashboard stats, nearby incident results, and later notification queues

Expo Push Notifications
    ↓
Sends mobile notifications to user phones

============================================================
1. LOGIN FLOW - MOBILE APP
============================================================

User opens Mobile App
    ↓
User enters email/password
    ↓
Mobile App sends login request to Supabase Auth
    ↓
Supabase Auth validates credentials
    ↓
Supabase returns access token + refresh token
    ↓
Mobile App stores token securely using SecureStore
    ↓
Mobile App calls Backend: GET /auth/me
    ↓
Backend runs auth.middleware.ts
    ↓
Backend verifies Supabase JWT
    ↓
Backend gets user_id from token
    ↓
Backend checks user profile and organization memberships using Prisma
    ↓
Backend may cache memberships in Redis for short time
    ↓
Backend returns user profile + roles + joined organizations
    ↓
Mobile App loads citizen/volunteer interface
    ↓
If user belongs to organizations, Mobile App shows Organizations section

Result
    ↓
Every logged-in user can use citizen side
    ↓
Volunteers also see assigned tasks
    ↓
Admins may see basic organization info, but full admin work is in Web App

============================================================
2. LOGIN FLOW - WEB APP
============================================================

User opens Web App
    ↓
User enters email/password
    ↓
Web App sends login request to Supabase Auth
    ↓
Supabase Auth validates credentials
    ↓
Supabase returns access token + refresh token
    ↓
Web App stores session/token securely according to frontend design
    ↓
Web App calls Backend: GET /auth/me
    ↓
Backend verifies JWT
    ↓
Backend checks organization memberships and roles
    ↓
Backend returns user role details
    ↓
Web App decides what to show

If user is ORG_ADMIN
    ↓
Show organization admin dashboard
    ↓
If user is admin of multiple organizations, show organization switcher

If user is SUPER_ADMIN
    ↓
Show platform/super admin dashboard

If user is only CITIZEN or VOLUNTEER
    ↓
Show No Admin Access page
    ↓
Tell user to use Mobile App for citizen/volunteer features

============================================================
3. CITIZEN REPORTS AN INCIDENT - MOBILE APP
============================================================

Citizen opens Mobile App
    ↓
Citizen taps Report Incident
    ↓
Mobile App opens CreateReportScreen
    ↓
Citizen enters title, description, category, severity
    ↓
Citizen takes/selects photo
    ↓
Mobile App compresses photo before upload
    ↓
Citizen selects location using GPS or map pin
    ↓
Mobile App prepares report data

Report data
    ↓
title
    ↓
description
    ↓
category
    ↓
severity
    ↓
photo file
    ↓
latitude + longitude
    ↓
optional organization/context

Mobile App sends request to Backend
    ↓
POST /incidents
    ↓
Backend runs auth.middleware.ts
    ↓
Backend verifies user token
    ↓
Backend runs validation
    ↓
Backend stores incident in PostgreSQL using Prisma
    ↓
Backend stores latitude + longitude
    ↓
Backend also stores PostGIS location field for nearby search
    ↓
Backend uploads/stores photo through file storage
    ↓
Backend creates status history record
    ↓
Incident status becomes Reported
    ↓
Backend creates notification for relevant organization admins
    ↓
Mobile App shows success message

Result
    ↓
Citizen can see the report in My Reports
    ↓
Organization admin can see the report in Web Dashboard

============================================================
4. ORGANIZATION ADMIN REVIEWS INCIDENT - WEB APP
============================================================

Organization Admin opens Web App
    ↓
Admin logs in
    ↓
Web App loads selected organization dashboard
    ↓
Admin opens Incidents page
    ↓
Web App calls Backend: GET /incidents?status=REPORTED
    ↓
Backend runs auth.middleware.ts
    ↓
Backend runs tenant.middleware.ts
    ↓
Backend confirms admin belongs to selected organization
    ↓
Backend runs role.middleware.ts
    ↓
Backend confirms user has ORG_ADMIN role
    ↓
Backend queries incidents only for that organization
    ↓
Web App shows incident list and map markers
    ↓
Admin clicks one incident
    ↓
Web App opens IncidentDetailsPage
    ↓
Admin reviews photo, description, map location, category, severity

Admin decision
    ↓
Verify incident
    ↓
OR
    ↓
Reject incident with reason

If verified
    ↓
Web App sends PATCH /incidents/:id/status
    ↓
Backend checks auth + tenant + role
    ↓
Backend updates incident status to Verified
    ↓
Backend writes status_history
    ↓
Backend writes audit_log
    ↓
Backend notifies citizen about status change

If rejected
    ↓
Backend updates status to Rejected
    ↓
Backend stores rejection reason
    ↓
Backend notifies citizen

Result
    ↓
Verified incident can become a cleanup task
    ↓
Rejected incident is closed with reason

============================================================
5. ADMIN CREATES CLEANUP TASK FROM VERIFIED INCIDENT - WEB APP
============================================================

Admin opens verified incident
    ↓
Admin clicks Create Cleanup Task
    ↓
Web App opens CreateTaskPage or modal
    ↓
Admin enters task title, instructions, scheduled date, required volunteers
    ↓
Task automatically uses incident location
    ↓
Admin submits task
    ↓
Web App sends POST /tasks
    ↓
Backend runs auth.middleware.ts
    ↓
Backend runs tenant.middleware.ts
    ↓
Backend runs role.middleware.ts for ORG_ADMIN
    ↓
Backend confirms incident belongs to same organization
    ↓
Backend creates task using Prisma
    ↓
Backend links task to incident_id
    ↓
Backend sets task status to Scheduled or Open
    ↓
Backend writes audit_log
    ↓
Backend returns created task
    ↓
Web App shows task details

Result
    ↓
Incident now has a linked cleanup task
    ↓
Admin can assign volunteers

============================================================
6. ADMIN ASSIGNS VOLUNTEERS TO TASK - WEB APP + NOTIFICATIONS
============================================================

Admin opens task details
    ↓
Admin clicks Assign Volunteers
    ↓
Web App calls GET /volunteers
    ↓
Backend returns volunteers belonging to same organization only
    ↓
Admin selects volunteers
    ↓
Web App sends POST /tasks/:taskId/assign
    ↓
Backend runs auth + tenant + role checks
    ↓
Backend creates task_assignments records
    ↓
Backend updates task status if needed
    ↓
Backend creates notification records in database
    ↓
Backend finds each volunteer's ExpoPushToken from user_devices table
    ↓
Backend sends notification to Expo Push Service
    ↓
Expo sends notification to Android/iOS
    ↓
Volunteer phone shows top-bar notification

Notification example
    ↓
Title: New cleanup task assigned
    ↓
Message: You have been assigned to a cleanup task near Bolgoda Lake
    ↓
Data: taskId + organizationId + notificationType

Result
    ↓
Volunteers receive task assignment immediately
    ↓
Task appears in My Tasks on Mobile App

============================================================
7. VOLUNTEER OPENS TASK AND UPDATES PROGRESS - MOBILE APP
============================================================

Volunteer receives notification
    ↓
Volunteer taps notification
    ↓
Mobile App opens TaskDetailsScreen using taskId from notification data
    ↓
Mobile App calls GET /tasks/:id
    ↓
Backend checks auth + tenant membership
    ↓
Backend confirms volunteer is assigned to this task or belongs to organization
    ↓
Backend returns task details
    ↓
Volunteer sees task title, instructions, location, date, status

Volunteer action
    ↓
Accept task
    ↓
Mark In Progress
    ↓
Mark Completed
    ↓
Upload completion evidence photo

Mobile App sends status update
    ↓
PATCH /tasks/:id/status
    ↓
Backend validates allowed status transition
    ↓
Backend updates task status
    ↓
Backend writes status_history
    ↓
Backend writes audit_log
    ↓
Backend notifies organization admin

If completion photo uploaded
    ↓
Mobile App compresses image
    ↓
Uploads image through backend/storage flow
    ↓
Backend stores file URL in database

Result
    ↓
Admin can see task progress in Web Dashboard
    ↓
Incident can be closed after admin review

============================================================
8. ADMIN CLOSES INCIDENT AFTER TASK COMPLETION - WEB APP
============================================================

Admin opens Web Dashboard
    ↓
Admin opens completed task
    ↓
Admin reviews volunteer notes and completion photo
    ↓
Admin confirms cleanup is completed
    ↓
Web App sends PATCH /incidents/:id/status = RESOLVED
    ↓
Backend checks auth + tenant + role
    ↓
Backend updates incident status to Resolved
    ↓
Backend updates task status to Closed if needed
    ↓
Backend writes status_history
    ↓
Backend writes audit_log
    ↓
Backend updates or invalidates Redis dashboard cache
    ↓
Backend notifies citizen and volunteers
    ↓
Web Dashboard analytics updates

Result
    ↓
Incident lifecycle is complete
    ↓
Citizen sees report status as Resolved
    ↓
Organization impact metrics improve

============================================================
9. ORGANIZATION SWITCHING FLOW - WEB APP
============================================================

Admin logs into Web App
    ↓
Backend returns list of organizations where user is ORG_ADMIN
    ↓
Web App shows organization switcher in top bar
    ↓
Admin selects Organization A
    ↓
Web App stores selected organization in frontend state
    ↓
All API requests include selected organization context
    ↓
Backend tenant.middleware.ts checks membership in Organization A
    ↓
Backend returns only Organization A data

Admin switches to Organization B
    ↓
Web App changes selected organization
    ↓
Next API calls use Organization B context
    ↓
Backend checks membership in Organization B
    ↓
Backend returns only Organization B data

Security rule
    ↓
Frontend organization switcher is not trusted alone
    ↓
Backend must always confirm membership and role
    ↓
Changing URL manually must not expose another organization's data

11. EXPO PUSH NOTIFICATION TOKEN REGISTRATION FLOW
============================================================

User logs into Mobile App
    ↓
Mobile App asks notification permission
    ↓
User allows notifications
    ↓
Expo returns ExpoPushToken
    ↓
Mobile App sends token to Backend
    ↓
POST /notifications/register-token
    ↓
Backend verifies JWT
    ↓
Backend stores token in user_devices table

Stored values
    ↓
user_id
    ↓
expo_push_token
    ↓
platform: android or ios
    ↓
is_active: true
    ↓
created_at

Later, when notification is needed
    ↓
Backend finds user token
    ↓
Backend sends message to Expo Push Service
    ↓
Expo sends notification to phone OS
    ↓
Phone displays notification

Important point
    ↓
Mobile app does not need to keep running in background
    ↓
Phone OS handles showing the notification

============================================================
12. BACKEND SECURITY FLOW FOR PROTECTED REQUESTS
============================================================

Frontend sends API request
    ↓
Authorization header contains Bearer access_token
    ↓
Request enters Express route
    ↓
auth.middleware.ts
    ↓
Verifies Supabase JWT
    ↓
Attaches req.user
    ↓
tenant.middleware.ts
    ↓
Finds organization context
    ↓
Checks user membership in organization
    ↓
Uses Redis cache first if available
    ↓
If not cached, queries PostgreSQL using Prisma
    ↓
Attaches req.tenant
    ↓
role.middleware.ts
    ↓
Checks required role for endpoint
    ↓
Allows or blocks request
    ↓
Controller
    ↓
Reads request and calls service
    ↓
Service
    ↓
Runs business logic and database operations
    ↓
Response returned to frontend

If error happens
    ↓
error.middleware.ts handles error
    ↓
Frontend receives clean error message

============================================================

Citizen selects incident location
    ↓
Mobile App gets latitude and longitude
    ↓
Mobile App sends location to Backend
    ↓
Backend stores latitude and longitude for easy display
    ↓
Backend also stores PostGIS geography point

Database values
    ↓
latitude
    ↓
longitude
    ↓
location = geography(Point, 4326)

Admin opens map dashboard
    ↓
Web App calls GET /incidents/map or /incidents/nearby
    ↓
Backend checks auth + tenant + role
    ↓
Backend queries incidents for selected organization
    ↓
For nearby search, backend uses PostGIS distance query
    ↓
Backend may cache result in Redis
    ↓
Web App displays markers on map

Result
    ↓
Admins can see where incidents are located
    ↓
Volunteers can see task locations
    ↓
Future advanced feature can show heatmap

14. REDIS USAGE FLOW
============================================================

Case 1: Role/membership cache
    ↓
User makes protected request
    ↓
Backend checks Redis for user role in organization
    ↓
If found, use cached role
    ↓
If not found, query database using Prisma
    ↓
Store result in Redis for short time

Case 2: Dashboard stats cache
    ↓
Admin opens dashboard
    ↓
Backend checks Redis for dashboard counts
    ↓
If cached, return quickly
    ↓
If not cached, calculate from PostgreSQL
    ↓
Store result in Redis for 1-5 minutes

Case 3: Nearby incident cache
    ↓
User requests nearby incidents
    ↓
Backend checks Redis for same area/radius query
    ↓
If cached, return quickly
    ↓
If not cached, query PostGIS
    ↓
Store result in Redis for short time

Case 4: Notification queue - advanced
    ↓
Task assigned
    ↓
Backend adds notification job to Redis queue
    ↓
Worker sends notification through Expo/FCM
    ↓
API response stays fast

============================================================
15. FRONTEND CACHE FLOW
============================================================

Web App / Mobile App uses TanStack Query
    ↓
User opens page/screen
    ↓
Frontend calls API
    ↓
TanStack Query stores response in frontend cache
    ↓
User switches page/screen
    ↓
User comes back
    ↓
Frontend shows cached data quickly
    ↓
If cache is stale, frontend refetches in background

Example cache values
    ↓
User profile: 5 minutes
    ↓
Joined organizations: 5 minutes
    ↓
Dashboard stats: 1-2 minutes
    ↓
Incident list: 30-60 seconds

Important point
    ↓
Frontend cache improves user experience
    ↓
Backend security must still be checked on every protected API request
